# 当前流量路由与可观察特征

当前为 moon-naive（0.6.0）。旧版 Basic、legacy8/16条及官方客户端互通描述不适用于当前源码。完整上游弱点证据、协议格式和客户端要求见 [PROTOCOL.md](PROTOCOL.md)。

外部被动观察者仍能看到IP、端口、包长、时序和部分握手信息；完成TLS的主动客户端只能看到自己的HTTP请求响应。正常链路中的CONNECT目标、认证和Padding头在TLS内加密，不能把它们描述成明文DPI标志。

## 2026-11-03 证书与请求矩阵

以TShark4.4.19完成97份正式本地抓包，使用四种临时自签CA方案：P-256只发送叶证书、P-256叶证书加根、RSA2048叶证书加根、P-384叶证书加中间CA加根。第一种仍是CA签发的叶证书，客户端显式信任CA；不是跳过验证接受任意自签叶证书。发送根证书仅用于实验比较，生产使用CA给出的正确完整链，不为改变指纹额外发送根。每种覆盖H1普通GET/HEAD/CONNECT/未知Host/歧义分帧，H2/H3网站/认证失败/8条或16条填充/稀疏模式，另含H2内层TLS；还测试复用、空闲及H3延迟/丢包。

分析分为**无keylog的被动视图**和**有测试keylog的解密视图**。TLS1.3记录使用tshark的opaque_type；脚本按每条记录的树结构取长度，避免把同包ServerHello/CCS与密文的平铺字段错配。H3 Retry后解码需要单独分析副本，原始pcap保持不变。解密得到的HTTP状态、认证首部及HPACK/QPACK长度，不能直接当作链路上的明文特征。

| --- | --- | --- |

四份TLS1.3/H1网站样本中，P-256叶证书、P-256完整链、RSA2048完整链、P-384中间链对应的首条服务端密文记录长度分别为**572、916、1893、1478字节**，不含5字节TLS记录头。这些记录携带加密握手数据，长度不等于证书DER长度；签名长度、证书内容及库的打包策略会改变数值，不能将它们写成固定识别规则。

H2 SETTINGS、窗口策略、QUIC Retry、包长/方向/时序、源站内容和内层TLS关联仍可能区分具体实现。抓包夹具H2最大并发流为8、初始流窗口65536，不要把夹具参数误写成生产默认值。证书类型也不改变HTTP库及其帧顺序。未对照真正Chromium客户端或Caddy同配置抓包，没有复测OpenGFW分类，也没有测真实审查网络的识别率。

根据证据修正的是发送调度和实验统计，没有删除逐流认证、响应证明、先拨号后200，也没有增加固定假流量或随机延迟。H3在具体本地工作负载中的改进及限制见[最新验证记录](VERIFICATION.md)；证书DER长度、被动指纹、请求状态及97份抓包哈希见[机器可读结果](packet-lab-results.json)。

## 当前Padding与首部行为

认证仅在TLS1.3 H2/H3上进行，绑定实际exporter、流ID和请求。成功CONNECT返回200，认证证明字段值在加密前为58字符；这不是固定58字节的网络包。不添加随机Padding首部或随机正文。H2证明设为never-index，固定quiche QPACK不动态插入，但字面量仍可能Huffman编码。源站网站正文、长度与正常首部不随机改写。

当前采用认证协商的8/16条初期窗口及可选稀疏后段；满载读块停止附加填充，不生成空闲假流量或修改真实反代内容。预算、线格式与客户端要求见[PROTOCOL.md](PROTOCOL.md)。

初期读取预算为最大padding预留空间，不用当次P抵消有效数据长度。无额外结束帧、纯填充、凑块等待、人工分片或随机延迟。部分发送保持同一Bytes，上传借用输入切片，完成初期后直接转发。HTTP/TLS/QUIC仍可拆分或合并记录；16375预算不是线上包大小保证。

TLS密文原本具有高熵；减少padding不等于降低密文字节熵。本轮避免持续改变长度和方向分布，并减少开销，但协商后的8/16条边界和有界扰动依然是设计选择，尚未证明符合网站统计分布或降低DPI识别率。原始流阶段仍可能保留目标TLS的长度/时序相关性。

## SNI、ECH、时序与长连接

普通TLS及QUIC Initial不自动隐藏SNI。默认关闭的实验性ECH隐藏ClientHelloInner，仍暴露IP/公开名称与大小时序；不解决证书信任错误，也不消除TLS-in-TLS的相关性。ECH和非ECH使用相同有限记录规则，不按ech_accepted切换填充分布。

保持数据可用即转发、正常背压和拥塞控制，不添加随机延迟、空闲保活或假请求。先拨号后200、新客户端再验证响应证明后上传会保留一定时序结构。站点前导请求、会话复用、重连退避和关闭策略需新客户端配合。TCP BBR取决于内核，quiche使用配置的BBRv2；两者不是相同实现。

一条CONNECT仍对应一个目标TCP连接，多个CONNECT可复用一条外层H2/H3会话；目标内部又可复用H2。流量方向、长连接、突发、IP信誉和相关性分析仍有效，不能承诺不可探测。

## 路由与主动响应矩阵

以下 H1 指生产配置 `h1=true`，H2/H3 指启用的对应入口。普通网站域名为配置 domain 或已配置的 ECH public_name；网站源站来自固定 upstream/route。H1 的 Proxy-Authorization 即使正确也不授予代理能力。

本表区分代理授权和正常网站处理，不判断请求者是不是DPI探测器。2026-11-02补查作者Caddy插件并修正无效WebSocket请求暴露通道额度、H2取消准入的轮询顺序；详细证据和未解决的负载/时序差异见[请求准入评审](NAIVE-REALITY-REVIEW.md#后续加固caddy-插件与请求准入)。

| 网络栈与输入 | 路由/动作 | 主动客户端可见的应用特征 |
| --- | --- | --- |
| H1：普通网站请求，凭据正确/错误/缺失 | 清理代理及伪造转发头 → 固定反代源站 | 正常源站状态/正文/缓存头，前端可 gzip；本域名网站响应带 Alt-Svc；无代理 Padding/407 |
| H1：CONNECT，凭据正确/错误/缺失 | 网站方法处理，不按 CONNECT 目标拨号 | 网站域名通常 405，未知 Host 404；有普通错误正文，无代理认证挑战 |
| H1：绝对 URI 请求 | 通过 authority/Host 校验后按固定网站路由；外部 Host 不进入通用代理 | 可为网站响应、404 或解析错误 400，不能指定任意源站 |
| H1：CL+TE、歧义长度、非法 CRLF/Connection 指定删除受信字段 | 原始头检查或解析器拒绝，连接关闭，源站不接收请求 | 通常 400；底层非法/不完整传输也可能直接关闭 |
| H1：慢速或不完整请求头、空闲 keepalive | 完整头部期限 10 秒到期关闭；每连接 1,000 次请求后关闭 | 可观察的连接关闭；不会一直占用配额 |
| H2/H3：已认证普通 CONNECT | 每流认证 → 目标语法/公网 ACL/配额 → DNS/拨号 → 成功才 200 | 成功响应仅有固定长度HMAC证明，无装饰性Padding；协商8/16条初期窗口，后段选择直通或稀疏记录；失败按实际校验/拨号错误返回状态 |
| H2/H3：已认证普通 HTTP(S) 请求到外部 origin | 按用户/origin 隔离的正向代理池，执行出站策略 | 普通目标响应；不加隧道 Padding 或本站 Alt-Svc |
| H2/H3：已认证普通请求到本站 | 固定网站反代 | 与普通网站一致；携带代理凭据本身不会把本站请求变成任意目标代理 |
| H2/H3：缺失、错误、重复或下划线别名凭据 | 不继承同连接其他流的认证；合法网站请求走固定反代 | 普通网站响应；CONNECT 通常 404/405；无代理 407 和隧道 Padding，不解析/拨号该 CONNECT 目标 |
| H1/H2/H3：网站 WebSocket | H1 Upgrade 或 H2/H3 扩展 CONNECT 仅到管理员固定路由；不要求 Naïve 认证。H2/H3先检查Host/版本/路由，再申请通道额度 | 合法 Upgrade/扩展 CONNECT 握手及长连接，无任意目标代理权限；无效H2/H3网站请求的404/400不因通道额度已满而变为503 |
| H2：非法字段、伪首部或协议错误洪泛 | h2/Pingora/共享校验层拒绝；严重错误关闭连接 | 400、RST_STREAM 或 GOAWAY 取决于失败层；超过协议错误 reset 阈值可见 ENHANCE_YOUR_CALM |
| H3：未知地址 Initial、无/错误 Retry token | 无有效地址绑定 token 不分配正常连接状态 | Retry、版本协商或静默丢弃；属于 quiche 驱动可观察特征 |
| H3：已通过 Retry 但 TLS 未完成 | 10 秒内未完成则释放连接和窗口配额 | 握手无法继续；不进入认证或目标拨号 |
| H3：非法头/trailers、超限或流错误 | 拒绝/取消该流，必要时关闭连接 | HTTP 错误、STOP_SENDING/RESET_STREAM 或连接错误，取决于失败层 |
| 任意栈：错误 TLS 报文、证书验证失败 | HTTP 路由前握手失败；客户端必须保持证书校验 | TLS alert/关闭或 QUIC 握手错误，不保证能返回网页 |
| 任意栈：配额耗尽 | 对应连接/流拒绝，不突破预算 | 关闭、拒绝流或错误响应；不是容量型 DDoS 防护承诺 |

对已认证请求发送畸形报文也先执行协议校验，不因凭据正确放行攻击。伪装网站的错误行为与隧道的认证后错误行为无需刻意一致。未知 Host 不自动转发到任意第三方站点。

## 验证与比较边界

当前“有效认证”专指moon-naive；Basic、缺失或重放证明按未认证处理。H2 TLS1.2可服务网站但不开放代理，H1无论凭据如何都不开放任意目标代理。普通网站WebSocket只去配置的固定源站，保持WebSocket原始数据。

BoringSSL改变服务端握手行为，不等于完整Chromium客户端指纹，也没有证据证明比Caddy的Go服务端更难识别。客户端栈与服务器栈角色不能混淆，Go服务端本身不等于代理。RC4的Rust gzip、无Pingora本地错误banner和共享缓冲已保留；源站内容与错误协议行为仍可被观察。

测试覆盖边界解析、真实H2/H3、跨流/跨连接重放拒绝、慢读/半关闭、网站和浏览器H3发现；本轮补充了下文的OpenGFW本地对照，仍无受审查网络封锁率或等条件吞吐/延迟结论。下一步需固定域名证书、真实客户端版本、网站内容、RTT/丢包/MTU与负载，比较纯反代、Caddy+官方客户端和新双端实现。


## 2026-10-29 本地抓包与H2写入修复

在标准TLS加密前增加每条H2外层连接最多16KiB的有界写缓冲，合并当前已经提交的切片，再交给BoringSSL。固定Pingora TLS适配层声称支持vectored write，内层实现实际只写第一个切片；h2的256字节切片因此反复形成273字节TLSCiphertext记录（含5字节TLS头共278字节）。此现象也存在于正常网站响应，不是代理独有标志。

缓冲按H2正常flush排空，不引入定时等待、随机延迟或空闲流量；Pending后保留同一写入指针、长度及偏移，保证SSL_write重试与部分写入正确。代价为每条H2连接16KiB缓冲及额外一次明文拷贝（默认128连接最多约2MiB，配置上限4096连接约64MiB）。尚未测端到端吞吐收益。

使用Wireshark/TShark 4.4.7、实验自签CA签发的叶证书和明确CA/SAN验证，固定本地BoringSSL/h2/quiche客户端。下表为第一次完整样本；每类额外三次重复得到相同273字节记录计数：

| 场景 | 修复前273字节记录数 | 修复后 | 服务端应用TLS记录总数（前→后） |
| --- | ---: | ---: | --- |
| H2网站：同连接两次96KiB响应 | 16 | 0 | 35→27 |
| H2有限16条：两个CONNECT | 48 | 0 | 101→53（其他重复可为102→54） |
| H2内层HTTPS：同隧道24次请求 | 26 | 0 | 79→53 |

完整矩阵为每版15场景（H1网站/CONNECT、H2/H3网站/失败认证，以及8/16有限与稀疏模式、H2内层TLS），另有每版9次H2重复，共48次抓包工作负载。H2逐流DATA字节等于客户端记录，H3重组STREAM检查无缺口、FIN终点和HTTP3 DATA长度，隧道DATA还与客户端保存的原始应用流逐字节比较。

TShark在本组QUIC Retry前后握手上发生重组混淆。H3解密使用仅保留最后一次Retry后数据的派生分析副本；原始PCAP始终保留，OpenGFW和原始包长统计只读取原始PCAP。旧baseline截尾数据已排除。

OpenGFW固定v0.4.3原版引擎和观察规则，以离线适配器重放。每版15个原始PCAP结果相同：9个TCP连接FET阴性，其中7个Trojan阴性、2个无结论；6个QUIC连接对这些TCP分析器不适用。SNI仍可见，TLS握手JA3S前后相同。Trojan规则在这些H2样本中主要统计外层握手后的早期flight，不足以说明内层TLS相关性已消失。独立控制还复现该版本首段TLS校验未激活：非TLS样本也可能命中其长度树。

因此本轮只证实减少一种固定写入分片规律，没有测得真实GFW识别率变化。8/16协商、填充预算和稀疏概率保持协议修订4；没有通过加大随机Padding来干预规则。应用记录仍不等同于网络包，正常控制帧、流控、多流调度和16KiB DATA边界仍可能产生短TLS记录。

实验是loopback合成负载，存在分段卸载且没有真实互联网RTT/丢包，客户端不是Chromium；没有验证ECH流量分布或公网审查效果。原始结果及复现脚本在reports/packet-lab/{before-final,after-final,before-repeat,after-repeat}，核心夹具在src/net/tests/capture.rs。测试TLS密钥只写实验目录，生产TLS未启用keylog。


## 2026-10-30 镜像反代、并发与连续下载

本次保留协议修订4的证明、8/16记录协商和填充概率，没有增加随机响应首部、虚假网页正文或空闲流量。改动是：

- H1固定长度反代响应保留Content-Length，仅未知长度响应补回chunked；真正压缩时由Pingora模块更新分帧。连续同一连接的固定正文、gzip、Range 206、未知长度、HEAD、304、204均验证通过。
- 有限填充结束后的原始隧道读取上限从16384降至16375字节，为H2的9字节DATA头留出TLS写入空间。不等凑满、不随机拆包、不改变字节内容；稀疏模式仍使用既有16309字节payload上限。读取窗口少9字节约0.055%，未做吞吐收益测试。
- H3成功响应的Date使用Pingora相同的按秒缓存，减少逐响应日期格式化。日期格式不变，不作为抗识别效果。

每个大文件场景使用一条外层H2连接、两条CONNECT，先发送24个有节奏的小资源片段，再各发送1 MiB连续数据。相同夹具前后各重复3次：

| 模式 | 修复前26字节TLS记录数 | 修复后26字节TLS记录数 | 总TLS记录数：前→后 |
| --- | --- | --- | --- |
| 有限8条 | 117 / 118 / 118 | 0 / 0 / 0 | 308 / 309 / 309 → 240 / 235 / 240 |
| 有限16条 | 117 / 117 / 117 | 0 / 0 / 2 | 308 / 308 / 308 → 235 / 240 / 241 |

这里26指TLSCiphertext的length字段，未含5字节TLS记录头；对应9字节内容加TLS1.3内层类型及AEAD开销。修复消除的是满块发送引入的重复溢出，控制帧、空DATA结束帧及多流调度仍可能产生小记录。TLS记录不等于IP包。初次bulk-before中一项抓包丢6包，整个阶段不用于结论；扩大dumpcap缓冲至64 MiB后的bulk-baseline全部完整。

32路并发镜像请求和32路CONNECT均仅用一条外层TLS/H2连接。冷H1源站在该夹具中建立32条回源连接；预热后的HTTPS/H2源站通过Pingora池以一条连接承载1次预热加32次请求。该结果验证既有池复用能力，并非本次新增连接池算法，也不能保证冷启动只建立一条连接。32个独立CONNECT仍需32条目标TCP连接，不能在服务端任意合并。

连续连接场景发送16个资源，穿插4次两秒空闲；测试空闲超时设为3秒，总会话超过8秒。网站和隧道均保持一条外层连接、一条源站/目标连接，正常活动延长空闲期限。四个空闲区间中段均无TCP payload（两侧各排除50 ms控制投递区间），未发送假流量。这里只验证跨多次空闲的复用和期限重置，不是长时间稳定性验收。

CONNECT仍需200表示转入隧道；普通镜像GET的正文、Content-Length、ETag不适用于成功CONNECT。第一条H2 CONNECT响应HEADERS在本轮样本为90–94字节，32路场景后续证明头为67–71字节；普通镜像响应复用首部表后多为24–26字节，日期变化另有增量。数值为HEADERS压缩块长度，不含9字节帧头，更不是TLS/网络包长。保留HMAC和never-index防止认证失效、凭据进入共享动态表。不能宣称隧道响应与镜像响应相同；首部加密也不等于长度侧信道消失。

本轮37项完整捕获覆盖修复各阶段，全部H2 DATA长度一致，8项H3捕获完成偏移/FIN/正文核验。固定OpenGFW v0.4.3离线引擎得到：29个TCP的FET阴性，Trojan 26个阴性、3个无结论；8个UDP不适用TCP分类器。大小文件修复前后没有分类改善。另重跑8项分类器正负对照，以及非TLS首段也可命中Trojan长度树的独立对照，均符合固定分析器行为。
